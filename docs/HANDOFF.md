# light-web: spec and handoff

## Why this exists

Will builds Light Phone III tools (light-dnd, light-training, light-amp...). Today the only way to
see one running is on the phone or in an Android emulator. The goal is to run those tools **in a
web browser**, from their real source code, not by streaming video of an emulator. That gives:

- a way to show and share tools with anyone who has a browser,
- an "LP3 emulator" that loads in a tab instead of a multi-GB Android image,
- a way to *use* a tool from a computer (bigger keyboard, no phone needed).

Two modes, switchable under the screen and remembered per browser:

- **LP3 emulator**: as close to the phone as possible, including Light's on-screen keyboard.
- **Computer**: same tool, but text fields take the computer's keyboard directly.

## Approach, and why this one

Light tools are Kotlin + Jetpack Compose on top of the Light SDK. Kotlin compiles to
WebAssembly, and JetBrains' Compose Multiplatform runs Compose in a browser (drawn to a
`<canvas>` with Skia). What doesn't exist in a browser is Android: the tools call Android and
Java APIs (files, logging, fonts, databases, dates).

Options considered:

1. **Emulate Android in wasm** (QEMU compiled to wasm). Possible in principle, unusably slow
   and huge. Rejected.
2. **Port each tool to multiplatform libraries.** The "proper" route, but means editing every
   tool, and maintaining two versions until Light's SDK goes multiplatform. Deferred.
3. **Compile tools unchanged, and supply the Android/Java APIs they call under the same names,
   built on browser features** (polyfills for Android). **Chosen.** Tools stay the source of
   truth; light-web never edits them.

Guiding rule: **upstream repos are read-only.** Fix things with a stand-in in `src/compat`, a
per-tool shim in `src/tools/<tool>`, or by excluding an upstream file and writing a web version
in `src/sdk`. A few exact text rewrites of the *copied* sources are allowed (`rewrites` in
`build.gradle.kts`); each fails the build if it stops matching.

## Decisions so far, and why

### Shape of the project

- **Compile tools unchanged; never edit upstream** (see Approach). Everything web-specific lives
  in light-web.
- **One SDK copy for all tools** (light-dnd's vendored v0.2.0). light-training's is identical.
  A tool on a different SDK version needs a decision first.
- **Develop first; hosting and a GitHub remote later** (Will, 2026-10-10). When a remote is
  made, start it private: that's a backup at once, and "public source?" and "public build?" stay
  separate decisions. A public build fits GitHub Pages (static files). Before anything goes
  public, check the light-keyboard licence allows redistributing a compiled build.
- **Akkurat is not bundled** (licence). SDK text uses the default font. A licensed copy in a
  pack's `res/font` is picked up automatically.

### Behaving like the phone

- **System back pops the screen directly**, like LightActivity's back callback. A view model's
  `onBackPressed` only applies when the tool calls `goBack()` itself.
- **Keys are heard on the page, not through Compose focus.** Focus is lost whenever the focused
  element leaves the screen.
- **Assets are fetched whole when a tool opens.** Android reads assets synchronously.
- **A tool crash reloads the page**, as Android ends the process. Measured first: an exception
  while composing leaves Compose dead (nothing redraws, Esc ignored) and `ComposeViewport` can't
  be torn down and remade; exceptions in clicks and coroutines leave the page alive but the tool
  half-done. So every uncaught exception while a tool is open reloads, and only then: an error
  in the shell itself doesn't, so it can't loop. Saved data survives (every store writes to
  localStorage before its save call returns). `?crashtest` keeps a tool that throws on purpose.

### Generated, not hand-copied

- **JVM-name shims come from one template** (`src/templates/JvmBuiltins.kt.template`), written
  into every upstream package. A name is left out of a package that declares it (light-dnd's
  `model.Character` clashed) or star-imports a package that does, since a package's own names
  beat star imports and ours would quietly win.
- **Tool registration is generated** from what Android's build reads too: id and label from
  `lighttool.toml`, entry point and first screen from `@EntryPoint`/`@InitialScreen`. The one
  thing that can't be generated, a hand-written Room database, is found by a `@WebDatabase`
  annotation, the same way.

### Libraries

- **Prefer a real multiplatform library under a stand-in when one has a wasm build.**
- **DataStore is an alpha** (1.3.0-alpha11), taken because it's the only line with a wasm build.
  Checked by hand: write, reload, read back, and the migration from our old JSON format. Move to
  the stable 1.3 when it ships. Cost: about 42 KB gzipped for the whole of step 4.
- **kotlinx-datetime is pinned at 0.7.1**, the version Compose Material 3 already brings in, so
  it costs nothing and can't drift from what Material 3 was built against. 0.8.0 exists.
- **`DateFormat` stays on the browser's `Intl`**: kotlinx-datetime has no localised formats.
  `Instant` was already on `kotlin.time`.
- **Room databases are hand-written per tool for now.** Will chose to let a general solution
  "earn its way in". Room 3 is now stable, which makes it cheaper than when that was decided;
  see the plan below.

### Working method

- **Test in headless Chromium, not Will's browser.** The Chrome extension may attach to the wrong
  profile, and its tab is often in the background (`hidden`), where nothing renders and
  screenshots time out. `chromium --headless=new --remote-debugging-port=...`, driven over CDP
  from Node's built-in WebSocket, needs nothing installed. The driver used so far lives outside
  the repo; worth bringing in as `tool/drive.mjs` if checks are to be repeatable.
- **Commit per step, then record the hash here.**

## Room 3: plan (researched 2026-10-10, nothing implemented)

### Why

light-training's database is `WebTrainingDatabase`: a hand-written stand-in for the code Room
generates, implementing the tool's DAO interfaces over JSON tables in localStorage. It mirrors
schema v11 by hand, nothing notices when upstream changes a query or the schema, and its queries
are approximations of the SQL (`COLLATE NOCASE` as a lowercase sort, and so on). Room 3 runs the
tool's own DAOs and SQL against real SQLite in the browser.

### What's established

Checked against the published artifacts and light-training's source:

- **Room 3 is stable**: `androidx.room3:room3-runtime` 3.0.3, with 3.1.0-alpha01; both publish
  `wasm-js` builds. (Earlier notes here called it an alpha; it no longer is.)
- **Its package is `androidx.room3`**, not `androidx.room`. light-training imports
  `androidx.room.*` (Room 2.7.0 on the phone, through the SDK's `buildDatabase`), so the tool
  can't compile against Room 3 without its imports changing.
- **The web driver is `androidx.sqlite:sqlite-web`** (2.7.1 stable, 2.8.0-alpha01):
  `WebWorkerSQLiteDriver(worker: Worker)`. You supply the web worker. It speaks a small JSON
  message protocol with four commands: `open`, `prepare`, `step`, `close`. No official worker
  is published on npm (`@androidx/sqlite-web-worker` doesn't exist). SQLite's own wasm build is
  `@sqlite.org/sqlite-wasm` (3.53.4).
- **light-training's DAOs are web-ready**: all 36 DAO functions in `model/TrainingDao.kt` are
  `suspend` or return `Flow`, which is what an asynchronous driver needs.
- **Schema history is exported**: `tool/src/main/assets/schemas/.../11.json`, which Room's
  compiler reads for auto-migrations (`room.schemaLocation`). light-training only allows
  auto-migrations (see the comment in `TrainingDatabase.kt`).
- `TrainingDatabase` has no `@ConstructedBy`.

### Not yet confirmed

- Whether Room 3 needs `@ConstructedBy(XConstructor::class)` plus an `expect object` on targets
  without reflection, as Room 2.7's multiplatform build does. If so, it has to be added to the
  copied `TrainingDatabase.kt` by a `rewrites` entry, with the `expect` declared in
  `src/tools/training`.
- Which storage the worker should use. OPFS through SQLite's `opfs-sahpool` VFS should work
  without COOP/COEP headers (which GitHub Pages can't send). The plain `opfs` VFS needs them.
- What it costs to download: the SQLite wasm binary is the bulk. Measure before deciding.
- Whether any Room 2 API light-training uses is gone or changed in Room 3.

### The work

1. **Spike (do this first, an hour or two):** add Room 3 + KSP to the wasm target, compile
   light-training's `model` package against it with the import rewrite, and see what the
   compiler and KSP say. That settles most of "not yet confirmed".
2. **Build:** apply the KSP Gradle plugin; `add("kspWasmJs", "androidx.room3:room3-compiler:3.0.3")`;
   point `room.schemaLocation` at the synced copy of the tool's `assets/schemas`.
3. **Import rewrite:** in copied tool sources only, `import androidx.room.` → `import
   androidx.room3.`. This is broader than today's exact-text `rewrites`, so give it its own
   step in `syncUpstreamSources` with its own check that it matched.
4. **Web worker:** a small JS worker over `@sqlite.org/sqlite-wasm` implementing the four
   commands, served next to the page; the SQLite wasm is fetched by the worker, not bundled into
   ours.
5. **`buildDatabase` (`src/sdk/.../LightDb.kt`):** build with Room 3's builder and
   `WebWorkerSQLiteDriver`, one database per tool and name as today. Drop `@WebDatabase`, the
   `databases` map on `LightTool`, and the `androidx.room` stand-ins in `src/compat`.
6. **Carry existing data across:** on first open, if localStorage has
   `lightweb:room:com.thelightphone.training/<name>`, read it with the JSON decoding from
   `WebTrainingDatabase`, insert it through the tool's own DAOs, then remove the key, as the
   DataStore migration did. Without this, any data already logged in a browser is lost.
7. **Delete `WebTrainingDatabase.kt`** (277 lines).
8. **Verify** in headless Chromium: every training flow, including the never-verified screens;
   reload persistence; the migration from the JSON data; size before and after.

### Risks

- The import rewrite means the browser build compiles the tool against a different major
  version of Room than the phone does. Fine while the tool sticks to suspend/Flow DAOs and
  auto-migrations; worth a line in light-training's README so nobody's surprised.
- More moving parts: KSP in this build, a worker, OPFS. Each can fail in ways the JSON tables
  can't.
- Recommendation: run the spike now that Room 3 is stable, and decide on its results. The
  hand-written database is fine while light-training's schema is quiet; it's the next schema
  change that makes it expensive.

## Layout

- `build.gradle.kts`: syncs sources from `../light-dnd` (tool + its vendored SDK `ui`/`shared`),
  `../light-training/tool`, `../light-keyboard/ui`; applies `rewrites`; generates an Android-style
  `R` class per resource pack and a resource table, the JVM-name shims (`generateJvmBuiltins`)
  and the tool registry (`generateToolRegistry`); copies assets to `assets/<pack>/`.
- `src/compat`: stand-ins under real names (`android.util.Log` on Kermit, `java.io.File` on
  localStorage, `java.time.*` on kotlinx-datetime, `androidx.room` annotations,
  `painterResource(R.drawable)`, `Font(R.font)`, `SystemFonts`, `Resources.getIdentifier`, ...).
  DataStore Preferences is the real androidx DataStore 1.3 (alpha), made in
  `src/sdk/lightweb/WebPreferencesDataStore.kt`.
- `src/sdk`: the SDK client rewritten for the web: `LightToolHost` (replaces LightActivity:
  back stack + lifecycle), `SimpleLightScreen`/`LightScreen`, `SealedLightContext`,
  `buildDatabase`, `Assets` loader, `DeviceMode`, web keyboard input, mode-switching
  `LightTextInputEditor`.
- `src/shell`: LightOS stand-in: LP3-sized screen (360×413 dp, whole-pixel scaling), tool list,
  greyscale toggle, page-level key listener (Esc = system back), `CrashGuard`.
- `src/templates/JvmBuiltins.kt.template`: JVM names used without an import; the build writes it
  into every upstream package, minus names the package declares itself.
- `src/tools/<pack>`: what a tool needs that the build can't generate: for light-training the
  hand-written `WebTrainingDatabase` (`@WebDatabase`). `src/tools/crashtest` is the `?crashtest`
  tool.

## Build and run

```bash
cd ~/Projects/light-web
JAVA_HOME=/home/will/.jdks/jbr-21.0.11 ./gradlew wasmJsBrowserDistribution
cd build/dist/wasmJs/productionExecutable && python3 -m http.server 8765
```

Full rebuild ≈ 1 min. Output ≈ 4.9 MB gzipped (1.5 MB app wasm, 3.3 MB Skia) plus each tool's
assets.

## Known issues and gotchas

- Kotlin 2.3.20's wasm compiler intermittently crashes reading its own previous output.
  `compileKotlinWasmJs` deletes that output first, and incremental compilation is off. If it
  recurs: `rm -rf build/kotlin build/classes`.
- A Kotlin name clash in generated code can surface as an internal compiler error
  (`FirTypeAliasSymbol cannot be cast to FirClassSymbol`), not a normal one. Seen when a shim
  shadowed a package's own class.
- A crash reloads the whole page, so a tool's in-memory state (and any other open tool's) goes
  with it, as a process death would on Android. Saved data survives.
- `WebTrainingDatabase` mirrors light-training's schema v11 by hand and won't notice changes.
